# 網路規格

> 依據：`FRONTLINE_WEB_PROJECT_SPEC.md` §2.4、§6.1、§10。Phase 4 開始實作，本文件先定義方向與約束。
> 數值都是起始參數，要以實際的網路測試與滿房負載測試調整。

## 1. 原則

- 一個 Colyseus 房間 = 一場對戰，上限 16 人、每隊 8 人。
- 伺服器擁有對戰狀態與所有最終結果：位置、血量、彈藥、射速、命中、擊殺、分數、目標。
- 客戶端只送「輸入」，不送結果：不送位置、不送傷害、不送命中目標 id。
- Colyseus 只提供房間、配對與狀態同步的基礎；移動權威、武器規則、命中驗證、延遲補償與對戰規則都由 FRONTLINE 自己實作。
- 高頻戰鬥同步不使用 Supabase Realtime、資料庫或 serverless function。

## 2. 傳輸

- 第一個多人里程碑使用 Colyseus 的 WebSocket（WSS）。
- 遊戲系統只透過應用層介面溝通，不直接呼叫 WebSocket：

```ts
interface IGameTransport {
  connect(room: RoomRequest): Promise<void>;
  sendInput(command: InputCommand): void;          // 高頻，可以丟
  sendReliable(message: ReliableMessage): void;    // 加入、離開、換裝、聊天等
  onSnapshot(handler: (snapshot: WorldSnapshot) => void): Unsubscribe;
  onEvent(handler: (event: ReliableEvent) => void): Unsubscribe;
  disconnect(): void;
}
```

- 量測封包率、延遲、抖動、遺失後，若 WebSocket 的 TCP 隊頭阻塞成為瓶頸，再評估以 WebTransport datagram 傳送高頻移動快照。可靠事件（加入、離開、物品欄、對戰結果）一律維持可靠傳輸。任何替代傳輸都要另外做瀏覽器相容與部署測試。

## 3. 模擬頻率

| 項目 | 起始值 |
|---|---|
| 伺服器固定 tick | 30 Hz |
| 狀態快照廣播 | 15–30 Hz，依頻寬與平順度決定 |
| 客戶端渲染 | 獨立迴圈，目標 60 FPS |

**與 Phase 1 的銜接**：Phase 1 的本機模擬是 60 Hz（`CLIENT_SIMULATION_HZ`）。Phase 4 接上伺服器時，客戶端預測步長必須與伺服器 tick 相同，重播才會一致：

- 移動規則已集中在 `packages/shared`，且都以 `dt` 為參數，換頻率不需要改規則。
- 預計做法：客戶端預測改用伺服器 tick（30 Hz），渲染以插值維持平順；若 30 Hz 手感不足，再評估把伺服器提高到 60 Hz 並量測 CPU 成本。
- 物理碰撞查詢在伺服器端同樣使用 Rapier（Node 版），以靜態地圖碰撞網格為準。

## 4. 訊息

### 4.1 輸入指令（客戶端 → 伺服器，每個 tick）

| 欄位 | 說明 |
|---|---|
| `seq` | 遞增序號；伺服器拒絕重複或過舊的序號 |
| `clientTime` | 客戶端時間戳，用於延遲補償與診斷 |
| `move` | 前後、左右軸（-1–1），量化傳送 |
| `buttons` | 位元旗標：衝刺、跳躍、蹲下、瞄準、開火、換彈… |
| `yaw` / `pitch` | 視角，量化傳送 |

### 4.2 開火請求（Phase 5）

| 欄位 | 說明 |
|---|---|
| `shotSeq` | 每把武器遞增；重複或跳號的請求不處理 |
| `inputSeq` | 開火當下的輸入序號，伺服器以此還原當時的視角與位置 |
| `aimYaw` / `aimPitch` | 只用來檢查與伺服器接受的視角是否合理，不直接採用 |

客戶端**不送**：命中目標、傷害值、射擊原點座標（原點由伺服器依已知的玩家位置與武器計算）。

### 4.3 世界快照（伺服器 → 客戶端）

只同步遊戲需要的狀態（主規格 §10.3）：玩家 id 與隊伍、位置與速度、yaw/pitch、姿勢與動畫狀態、目前武器、血量與生死、相關裝備狀態、比分與目標狀態。另外附上「最後處理的輸入序號」供客戶端修正。

不同步：靜態地圖幾何、純視覺的粒子狀態、每根骨骼。

## 5. 客戶端預測與插值

- 本地玩家立即套用自己的輸入，並保留尚未被確認的輸入佇列。
- 收到快照後：回到伺服器狀態，丟掉已確認的輸入，重播其餘輸入（reconciliation）。誤差小時平滑修正，大時直接校正。
- 其他玩家以快照插值顯示，延遲約 2 個快照間隔。
- 外插只允許在保守的時間上限內。
- 亂序或過舊的快照直接忽略。

## 6. 命中驗證（Phase 5）

每一個開火請求，伺服器都要檢查（主規格 §6.1）：

1. 玩家屬於這場對戰，而且活著、可以開火。
2. 武器已裝備且有彈藥，換彈狀態允許開火。
3. 射速與射擊模式合法（伺服器依武器資料計時，容許少量網路抖動）。
4. `shotSeq` 合法且沒有重複。
5. 視角與伺服器接受的視角差距在合理範圍內。
6. 射擊原點由伺服器依已知位置計算，不採用客戶端座標。
7. 射線在伺服器端與目標 hitbox 相交，且沒有被地圖碰撞擋住。

### 6.1 散佈的亂數種子

舊版 UE5 骨架讓客戶端自己產生亂數種子，伺服器直接採用。作弊者可以挑選散佈最小的種子。Web 版改為：

```text
seed = hash(伺服器配發的對戰種子, 玩家 id, 武器欄位, shotSeq)
```

兩端都算得出同一個種子，但客戶端無法挑選。散佈的輸入（bloom、是否移動、姿勢）也由 `packages/shared` 的同一份函式計算，並以測試確認兩端結果相同。

### 6.2 延遲補償

基本的權威開火流程可以運作之後，再加入有上限的回溯：伺服器保存最近一段時間（例如 200–300 ms，依實測調整）的玩家 hitbox 歷史，依開火請求對應的時間點回溯判定。超過上限的請求以伺服器目前狀態判定。

## 7. 斷線與重連

- 偵測連線中斷後，保留玩家的位置一段可設定的時間。
- 期限內以同一身分重連可以取回位置與狀態。
- 超過期限則回到大廳。
- 防止重複連線，也防止重複的擊殺或計分事件。
- 人數不符合對戰規則時，結束對戰或重新分隊。

## 8. 防作弊基準

- 伺服器權威：血量、彈藥、射速、命中、擊殺、死亡、分數、目標。
- 驗證移動速度、加速度、跳躍頻率、姿勢切換、世界邊界。
- 驗證訊息大小、頻率、序號與結構。
- 拒絕不可能的移動與開火請求；記錄可疑行為供人工檢查。
- 驗證與加入對戰的請求要限流。
- 客戶端混淆不能取代伺服器權威，也不宣稱 MVP 能防止所有作弊。

## 9. 量測項目

依主規格 §15.2：房間 tick 耗時與漂移、每個對戰程序的 CPU 與記憶體、房間數與連線數、每秒收發的訊息數與位元組、RTT、抖動、斷線率、快照大小與頻率、驗證拒絕次數與可疑輸入數、對戰完成率與當機率。
